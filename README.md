# 🧠 What Is JobMarket AI?

**JobMarket AI** is an AI-powered career intelligence platform designed to transform raw job-market data and personal career information into **actionable, explainable career insights**.

Instead of being just another job board, the platform connects:

```text
┌──────────────────────────────────────────────────────────────────┐
│                         JOBMARKET AI                             │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  👤 YOUR PROFILE       📄 YOUR RESUMES       💼 JOB MARKET       │
│         │                     │                    │              │
│         └─────────────────────┼────────────────────┘              │
│                               ▼                                   │
│                     🧠 INTELLIGENCE ENGINE                       │
│                               │                                   │
│          ┌────────────────────┼────────────────────┐              │
│          ▼                    ▼                    ▼              │
│      🔎 MATCHING         📊 ANALYTICS         🤖 AI ASSISTANT    │
│          │                    │                    │              │
│          └────────────────────┼────────────────────┘              │
│                               ▼                                   │
│                  🚀 ACTIONABLE CAREER PLAN                       │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### The platform can help answer questions like:

* **How well does my resume match this job?**
* **Which skills am I missing?**
* **Which missing skills are critical?**
* **What should I learn next?**
* **Which projects should I build?**
* **How does my resume perform against ATS-style checks?**
* **Which jobs should I save and track?**
* **What skills are appearing together in the market?**
* **What skill clusters exist across analyzed jobs?**
* **Is there enough historical data to forecast skill demand?**
* **Can an AI assistant answer questions using my actual career data?**

# 🧩 Core Intelligence

## 🎯 Resume ↔ Job Matching

The matching engine combines several explainable signals:

```text
                  MATCH ENGINE
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Skills       Experience      Education
       40%            15%             10%
        │              │              │
        └──────────────┼──────────────┘
                       │
              ┌────────┴────────┐
              ▼                 ▼
        Keyword Coverage   Semantic Similarity
             15%                 20%
              │                 │
              └────────┬────────┘
                       ▼
                OVERALL SCORE
```

### Matching features

* Skills compatibility
* Experience comparison
* Education comparison
* Keyword coverage
* TF-IDF + cosine semantic similarity
* Weighted overall score
* Automatic weight renormalization when data is missing
* Critical / Important / Optional skill gaps
* Market-wide optional skill suggestions
* Ownership isolation
* Re-analysis without duplicate reports

> Match scores are explicitly presented as **estimates, not guarantees of employment**.

---

# 📈 Explainable Scoring

One important design principle is:

> **Missing data should not automatically become a zero.**

Every matching sub-score can return:

```text
score
  │
  ├── 0.0 → valid score
  ├── 1.0 → valid score
  └── None → insufficient data
```

When a component is unavailable, the overall score renormalizes the remaining weights instead of artificially dragging the candidate's score toward zero.

### Default weighting

```text
Skills              ████████████████████ 40%
Semantic Similarity ██████████           20%
Keyword Coverage    ███████              15%
Experience          ███████              15%
Education           █████                10%
```

These weights are deliberately treated as a **reasonable starting point**, not as empirically optimized truth.

# 🧠 Skill Gap Intelligence

Missing skills are classified into three levels:

### 🔴 Critical

Required by the job but missing from the user's skills.

### 🟠 Important

Preferred by the job but missing from the user's skills.

### 🔵 Optional

Not explicitly requested by the job, but frequently associated with its skills across the collected market dataset.

```text
JOB REQUIREMENTS
       │
       ▼
┌─────────────────────┐
│ Skill Gap Engine    │
└─────────┬───────────┘
          │
    ┌─────┼─────┐
    ▼     ▼     ▼
 Critical Important Optional
    │     │     │
    └─────┼─────┘
          ▼
   CAREER ROADMAP
```

Optional suggestions intentionally remain empty when the market dataset is too small.

# 🤖 AI Career Assistant

The AI assistant lives at:

```text
/assistant/
```

It uses the centralized AI provider architecture introduced earlier in the project.

### Grounding architecture

This application intentionally does **not** use vector RAG for the assistant's personal career data.

Instead:

```text
User Data
   │
   ├── Profile
   ├── Skills
   ├── Resumes
   ├── Jobs
   ├── Match Reports
   └── Saved Jobs
          │
          ▼
   Structured Context
          │
          ▼
      System Prompt
          │
          ▼
    AI Provider Manager
          │
          ▼
       AI Response
```

The reason is simple:

> The user's personal dataset is small, structured, and already available in the database.

That makes structured retrieval:

* cheaper
* easier to audit
* easier to test
* easier to reason about
* less likely to retrieve irrelevant personal information

The assistant is instructed to answer only from the supplied context and clearly state when information is unavailable.

# 🔌 Multi-Provider AI Architecture

JobMarket AI supports a provider-agnostic architecture:

```text
                         ┌─────────────────────┐
                         │ AIProviderManager   │
                         └──────────┬──────────┘
                                    │
             ┌──────────────────────┼──────────────────────┐
             │          │           │          │            │
             ▼          ▼           ▼          ▼            ▼
          Gemini      Groq      OpenRouter   Claude       OpenAI
             │
             ▼
      Gemini Key Rotation
       ┌────┬────┬────┬────┐
       │ K1 │ K2 │ K3 │ K4 │
       └────┴────┴────┴────┘
```

### Supported providers

* Google Gemini
* Groq
* OpenRouter
* Anthropic Claude
* OpenAI

Every provider implements the same interface.

This means application routes do not need to know which provider is being used.

# 🔄 Gemini Key Rotation

Gemini supports automatic multi-key rotation.

When a key encounters a retryable condition:

```text
Request
  │
  ▼
Key #1
  │
  ├── Success ───────────────► Done
  │
  └── Rate Limit / Quota
             │
             ▼
       Cooldown Key #1
             │
             ▼
          Key #2
             │
       ┌─────┴─────┐
       ▼           ▼
    Success      Failure
       │           │
       ▼           ▼
      Done       Key #3
```

Retryable failures include:

* rate limits
* quota errors
* 401 / 403
* 5xx responses
* network failures

A 400-level request error is not blindly retried through another key.

# 🧠 AI Response Caching

Responses are cached using a provider/model-aware key:

```text
(provider
 + model
 + method
 + prompt
 + extra context)
        │
        ▼
   AICacheEntry
```

This prevents a fallback provider from accidentally receiving a cached answer generated by another provider.

```text

```

Otherwise:

```text
Not enough historical data
        │
        ▼

```

### Forecast methodology

* One month ahead
* Linear extrapolation
* Only skills appearing in every month
* Volatility band based on observed movement
* Explicit methodology shown in UI
* No external market data
* No fabricated growth percentage

The UI explicitly states that the forecast is:

> **An estimate based on this deployment's own collected data — not a market prediction, and not based on any external data source.**

This feature intentionally refuses to produce a forecast on a fresh deployment.

# 🧾 Audit Logging

Administrative and security-sensitive events are stored through:

```text
ActivityLog
     │
     ├── Actor
     ├── Action
     ├── IP
     ├── Timestamp
     ├── User Email
     └── Sanitized Description
```

Logged events include:

* Registration
* Successful login
* Failed login
* Disabled-account login attempts
* Password changes
* Password resets
* Account deletion
* Administrative actions

### Important design decision

The user's email is denormalized onto the audit record.

The relationship uses:

```text
ON DELETE SET NULL
```

rather than cascade deletion.

Therefore:

```text
Delete Account
      │
      ▼
User deleted
      │
      ▼
Audit trail remains
```

An account cannot erase its historical audit trail simply by deleting itself.

The `_redact()` mechanism acts as a safety net.

# 🔐 Security Headers

Every response receives security headers including:

```text
X-Content-Type-Options
X-Frame-Options: DENY
Referrer-Policy
Permissions-Policy
Content-Security-Policy
```

HSTS is enabled only outside debug mode.

This prevents a development HTTP environment from accidentally teaching the browser to enforce HTTPS.

The limitation is documented rather than hidden behind a misleadingly "strict" security claim.

```json
}
```

Database failure returns:

```text
HTTP 503
```

with:

```json
{
  "status": "degraded"
}
```

The endpoint requires no authentication so that load balancers and uptime monitors can use it.

# 🐛 Important Engineering Lessons

## SQLAlchemy relationship ordering

A subtle bug was discovered in AI conversation history.

The relationship had:

```python
order_by="AIMessage.id"
```

and attempting:

```python
conversation.messages.order_by(AIMessage.id.desc())
```

did not replace the relationship ordering.

It effectively produced:

```sql
ORDER BY id ASC, id DESC
```

which remained ascending.

### Correct approach

Query the model directly:

```python
AIMessage.query.filter_by(...)
```

when a different ordering is required.

## 🧪 Test Harness Lesson

A temporary `curl` issue initially looked like a routing problem.

The combination of:

```bash
--data-urlencode
```

and redundant:

```bash
-X POST
```

produced misleading `405` results in fragmented scripts.

Direct Flask test-client verification and a corrected curl command confirmed the routes themselves were functioning correctly.

This was a testing-harness issue, not an application defect.

# 🧹 Dependency Reliability

A real dependency bug was discovered during fresh-clone verification.

`fpdf2` had previously been installed manually but was missing from:

That meant a fresh environment could install successfully but fail when PDF export was first used.

# 🔐 User Isolation Model

A core security contract runs through the application:

```text
Authenticated User
       │
       ▼
Current User ID
       │
       ▼
Ownership Query
       │
 ┌─────┴─────┐
 ▼           ▼
Owned      Foreign
Data       Resource
 │           │
 ▼           ▼
200       404 / 403
```

Private resources are never trusted merely because an ID was supplied by the browser.

The system validates ownership at the database/query and route levels.

# 🚧 Known Design Boundaries

This project intentionally documents what it does **not** claim.

### Forecasting

Requires enough historical data.

### AI providers

Successful live generation requires valid provider credentials.

### Semantic matching

Currently uses TF-IDF + cosine similarity.

### Assistant retrieval

Uses structured user-data grounding rather than vector RAG.

### CSP

Still requires `'unsafe-inline'` because inline scripts/styles remain in some templates.

### Learning resources

Curated URLs are manually maintained and are not automatically live-checked.

### Roadmap history

`CareerRoadmap` is currently one roadmap per user. Historical roadmap versions would require a dedicated history model.

### Application history

`SavedJob.status` intentionally represents the lightweight application funnel. Rich multi-round application history would require a separate model.

# 🧠 Engineering Principles

<div align="center">

### **1. Don't invent data.**

Real data beats plausible-looking AI output.

### **2. Don't hide uncertainty.**

If the dataset is insufficient, say so.

### **3. Prefer explainable algorithms.**

TF-IDF, deterministic heuristics and explicit scoring are used where appropriate.

### **4. Fail gracefully.**

No provider configured ≠ provider failure.

### **5. Keep users isolated.**

Ownership boundaries are tested, not assumed.

### **6. Test behavior, not just status codes.**

A `200` response is not enough.

### **7. Production should be different from development.**

Migrations, Gunicorn, persistence and health monitoring matter.

### **8. Security should survive mistakes.**

Validation, redaction, CSRF and ownership checks provide defense in depth.
