## 🧠 What Is JobMarket AI?

**JobMarket AI** is a data-driven career intelligence platform that connects a user's **resume, skills, target jobs, market data, learning roadmap, and career decisions** into one system.

Instead of relying entirely on generic AI suggestions, the platform prioritizes **real collected data and explainable algorithms**, using AI where generative reasoning actually adds value.

```text
                    ┌──────────────────────┐
                    │      USER PROFILE    │
                    └──────────┬───────────┘
                               │
                 ┌─────────────▼─────────────┐
                 │      RESUME ANALYSIS      │
                 └─────────────┬─────────────┘
                               │
              ┌────────────────▼────────────────┐
              │       JOB MARKET ANALYSIS       │
              └────────────────┬────────────────┘
                               │
                 ┌─────────────▼─────────────┐
                 │    RESUME ↔ JOB MATCHING  │
                 └─────────────┬─────────────┘
                               │
                    ┌──────────▼──────────┐
                    │    SKILL GAP DATA   │
                    └──────────┬──────────┘
                               │
             ┌─────────────────▼─────────────────┐
             │ CAREER ROADMAP + RECOMMENDATIONS │
             └─────────────────┬─────────────────┘
                               │
             ┌─────────────────▼─────────────────┐
             │  AI ASSISTANT + ADVANCED INSIGHTS│
             └───────────────────────────────────┘
```

> **Core philosophy:**
> **Real Data → Explainable Analysis → Deterministic Results → Optional AI Enhancement**

# 🎯 Resume ↔ Job Matching

The matching engine evaluates compatibility between a user's resume and a job.

### Matching dimensions

| Metric              |  Weight |
| ------------------- | ------: |
| Skills              | **40%** |
| Semantic Similarity | **20%** |
| Keywords            | **15%** |
| Experience          | **15%** |
| Education           | **10%** |

These are configurable starting weights rather than empirically optimized values.

---

## 🧮 Explainable Scoring

Semantic similarity uses:

```text
TF-IDF + Cosine Similarity
```

instead of a deep embedding model.

The interface is intentionally stable:

```python
semantic_similarity(text_a, text_b) -> float | None
```

This allows embeddings to replace TF-IDF in a future implementation without changing the calling code.

---

## Missing Data

The system does not automatically convert missing information into zero.

A metric can return:

```python
None
```

when insufficient information exists.

The overall score then renormalizes the available weights.

This prevents missing data from unfairly destroying an otherwise valid match score.

# 🧩 Skill Gap Analysis

Skill gaps are classified into three levels.

### 🔴 Critical

Required by the job but missing from the user's skills.

### 🟡 Important

Preferred by the job but missing from the user's skills.

### 🟢 Optional

Not explicitly required by the job but frequently associated with its skills across the collected market dataset.

Optional recommendations disappear when the available market data is insufficient.

> Match scores are estimates and **do not guarantee employment**.

# 🔄 Provider Fallback

The manager uses:

```text
Configured Default Provider
          ↓
AI_PROVIDER_ORDER
          ↓
Next Available Provider
          ↓
NoProviderAvailableError
```

Providers without credentials are skipped.

When all available providers fail, the system reports which providers were attempted and why.

Adding another provider does not require rewriting application routes.

---

# 🔑 Gemini Multi-Key Rotation

Gemini supports:

```text
GEMINI_API_KEY_1
GEMINI_API_KEY_2
GEMINI_API_KEY_3
GEMINI_API_KEY_4
```

When a key encounters a retryable error, it can enter cooldown and the next available key is attempted.

The architecture handles conditions such as:

* Rate limits
* Quota failures
* Authentication/authorization failures
* Server failures
* Network failures

Successful keys remain preferred when possible.

# 📈 Skill Demand Forecasting

Available at:

```text
/advanced/forecast
```

Forecasting is intentionally difficult to trigger.

A forecast requires:

```text
3+ months of history
        AND
3+ analyzed jobs per month
```

The model then:

* Forecasts one month ahead.
* Uses linear extrapolation.
* Displays the forecasting method.
* Calculates a volatility band.
* Forecasts only skills present in every historical month.
* Clearly labels the result as an estimate.

### Why so strict?

Career-market forecasting can produce convincing but unsupported numbers.

Therefore:

> **No sufficient data = No forecast**

This is intentional.

A fresh installation should correctly refuse to produce a forecast.

# 🔒 CSRF Protection

Authenticated state-changing API requests use a double-submit cookie mechanism.

```text
Random CSRF Token
       ↓
Cookie
       ↓
Frontend
       ↓
X-CSRF-Token Header
       ↓
hmac.compare_digest()
       ↓
Request Allowed / Rejected
```

Dedicated regression tests cover CSRF behavior.

# 👤 Ownership Isolation

Ownership is always derived from the authenticated session.

The application never trusts a user ID supplied by the client to determine ownership.

Helpers include:


Unauthorized private resources are generally returned as `404` rather than exposing their existence.

* Spoofed user IDs

## Audit Trail Protection

The user's email is denormalized onto the audit record.

The user relationship uses:

```text
ON DELETE SET NULL
```

rather than cascading deletion.

Therefore:

```text
Delete User
     ↓
User removed
     ↓
Audit Record remains
```

The audit history cannot be erased simply by deleting the associated account.

---

# 🚨 Sensitive Data Redaction

The audit layer includes a defensive `_redact()` function that attempts to remove values resembling:

* Passwords
* API keys
* Bearer tokens

This acts as a backstop against accidental sensitive-data logging.

---

The project goes beyond simply checking whether an endpoint returns `200`.

Tests validate actual behavior and data correctness.

Examples include:

```text
PDF bytes
   ↓
%PDF-
   ↓
Valid PDF
   ↓
Parse with pypdf
   ↓
Verify real resume data
```

JSON reports are checked for actual parsed information.

Recommendation tests verify that technologies come from real skill-gap data.

Security tests verify that unauthorized users cannot create or access private records.

---

# 🌐 AI Testing Strategy

Because provider credentials and network access may not always be available, AI functionality is tested in multiple layers.

### Layer 1 — Mocked HTTP

Tests verify:

* Request payloads
* Response parsing
* Error handling
* Fallback logic
* Caching
* Usage tracking
* Key rotation

### Layer 2 — Live Network Smoke Test

A real request can be sent to Anthropic using an intentionally invalid key.

This verifies:

```text
Application
     ↓
AI Manager
     ↓
Provider
     ↓
Real HTTPS
     ↓
Real 401
     ↓
Correct Error Classification
```

### Layer 3 — Full Live Pipeline

When configured, the complete provider pipeline can be exercised:

```text
AIProviderManager
       ↓
Provider Selection
       ↓
HTTP Request
       ↓
Provider Response
       ↓
Error Classification
       ↓
Fallback
       ↓
AIUsage Logging
```

Successful AI generation cannot be verified without valid credentials.

# 🧱 Important Architecture Decisions

## Real Data First

The application prefers real database-derived results over unsupported AI claims.

Used for:

* Market statistics
* Skill gaps
* Match scores
* ATS analysis
* Roadmaps
* Project recommendations
* Skill relationships
* Forecasting

---

## Lightweight NLP

The project intentionally uses:

```text
TF-IDF
Cosine Similarity
KMeans
```

before introducing expensive embedding infrastructure.

---

## Structured RAG

The AI assistant currently uses structured database retrieval rather than vector search.

If future versions need to search thousands or millions of market records, the existing embedding interface can be extended into a true vector-retrieval system.

---

## Graceful Degradation

AI is an enhancement, not a requirement for core functionality.

```text
No AI Key
   ↓
Core Application Still Works
   ↓
Deterministic Features Remain Available
```

---

# ⚠️ Known Limitations

* Real AI generation requires valid provider credentials.
* Real Gemini key rotation requires real rate-limit/quota responses.
* Live provider testing depends on network access.
* TF-IDF is currently used instead of deep embeddings for matching.
* AI Assistant grounding currently uses structured retrieval.
* Forecasting requires sufficient historical data.
* Forecasting currently uses linear extrapolation.
* Project recommendations are deterministic.
* Learning-resource URLs are manually curated.
* CSP still permits `'unsafe-inline'`.
* AI cache entries do not yet have a dedicated administration interface.
* Application tracking is intentionally lightweight.
* The AI assistant does not currently have a dedicated per-user daily question quota beyond existing application-level rate limiting.

# 🧪 Development Lessons

## SQLAlchemy Ordering

A relationship with an existing `order_by` can behave unexpectedly when another ordering is applied through the relationship.

The assistant's conversation history initially encountered this issue.

The solution was to query `AIMessage` directly whenever a different ordering was required.

### General rule

```text
Relationship with default ordering
              ↓
Need different ordering?
              ↓
Query the model directly
```

---

## Security Tests Should Test Security Properties

A security test does not always need to assert a specific HTTP status.

The important question is:

```text
Was unauthorized data accessed or modified?
```

For example, form validation may reject an invalid cross-user resource before the route's explicit authorization check.

The security requirement is still satisfied if:

```text
No unauthorized record is created.
```

# 📐 Data Model Principles

### Match Reports

One report per:

```text
(resume_id, job_id)
```

Re-analysis updates the existing report.

Historical trends should use a separate history table.

---

### Career Roadmap

Currently:

```text
One roadmap per user
```

Historical roadmap versions should use a dedicated history model.

---

### Saved Jobs

Current statuses:

```text
saved
applied
interview
offer
rejected
```

A richer application-history system should use additional models rather than overloading `SavedJob`.

---

### Skill Gap Source of Truth

The roadmap and recommendation systems use:

```text
gather_gap_skills()
```

as the shared source for determining what the user needs to learn.
